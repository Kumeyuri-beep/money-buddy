# merge_settings: แก้ช่องแข่งเขียน settings (12 พ.ย. 2569)

## ปัญหา
หน้าเว็บ "อ่านค่าตั้งค่าทั้งก้อน แล้วเขียนทั้งก้อน" ถ้าผู้ใช้เปิดสองแท็บแล้วบันทึกเหลื่อมกัน การบันทึกของแท็บหนึ่งอาจเขียนทับค่าอื่นที่อีกแท็บเพิ่งบันทึก (เสียเฉพาะค่าตั้งค่า ไม่ใช่ยอดเงิน) security-auditor ระบุไว้ตอน #78 เจ้าของสั่งเก็บเป็น backlog แล้วสั่งทำเมื่อ 12 พ.ย. 2569

## ทางที่เลือก (ตัวที่แนะนำ)
RPC `public.merge_settings(p_patch jsonb, p_remove text[])` รวมค่าฝั่งฐานข้อมูลในคำสั่งเดียว (`insert ... on conflict do update set value = (value - remove) || patch` ล็อกแถวระหว่างเขียน) คีย์ที่ไม่ส่งคงเดิมเสมอ
- security invoker (RLS ของ `settings` ยังคุม) · ต้องล็อกอินและเปลี่ยนรหัสผ่านแล้ว (`private.can_use_data`) · execute เฉพาะ `authenticated` · เพดาน 16 KB ของตารางยังบังคับ · migration แบบเพิ่ม (ไม่มี drop/delete)
- ทางอื่นที่ไม่เลือก: ล็อกแบบ optimistic (ใส่เลขเวอร์ชันในแถว) ต้องเพิ่มคอลัมน์และให้ผู้ใช้เจอข้อความขัดแย้ง · อ่านซ้ำก่อนเขียน (ลดช่วงแต่ไม่หายไป)

## ฝั่งเว็บ
- `LedgerRepository.patchSettings(patch)` ใหม่: ค่า = ตั้ง · `null` หรืออาร์เรย์ว่าง = ลบ · `undefined` = ไม่แตะ · ออนไลน์เรียก RPC, ในเครื่องใช้ธุรกรรมเดียว
- `saveSettings` เดิม (แทนทั้งชุด ยกเว้นแผน DCA และรายชื่อเกษียณที่ไม่ส่ง = คงเดิม) ทำผ่าน RPC เดียวกัน พฤติกรรมเดิมไม่เปลี่ยน (มีเทสต์สัญญาทั้งในเครื่องและออนไลน์)
- DcaPlansCard และหน้าเกษียณ เปลี่ยนเป็น `patchSettings` ส่งเฉพาะคีย์ของตัวเอง
- ยังเหลือ: แท็บสองแท็บแก้ "แผน DCA" พร้อมกัน ยังทับกันได้ในคีย์เดียวกัน (ทั้งก้อน dcaPlans) ไม่กระทบค่าอื่น

## ผลตรวจ security-auditor (ไม่พบระดับสูง · ไม่มีทางรั่ว/แก้ข้ามผู้ใช้)
- **ยอมรับ (บันทึกไว้):** (1) แท็บสองแท็บแก้ "แผน DCA" พร้อมกันยังทับกันภายในคีย์ `dcaPlans` (ทั้งก้อน แท็บหลังชนะ) ปิดจริงต้องมี RPC เพิ่ม/ลบทีละรหัส หรือส่งค่าเดิมที่คาดไว้ (`p_expect`) — เลื่อนไว้ ไม่กระทบค่าตั้งค่าอื่นและไม่ใช่ยอดเงิน (2) ฟอร์มค่าตั้งค่าหน้าบิลยังส่งคีย์ของฟอร์มเองครบชุด (เจ้าของคีย์ 4 ตัวคือฟอร์มนั้น) แท็บหลังชนะเฉพาะ 4 คีย์นั้น ถ้าจะให้ส่งเฉพาะช่องที่แก้จริงเป็น Ticket ถัดไป
- **ยอมรับ (ต่ำ):** RPC ไม่กรองคีย์นอกรายการ 6 ตัวฝั่งเซิร์ฟเวอร์ (ผู้ใช้เรียกตรงๆ ใส่คีย์ขยะของตัวเองได้ เดิมก็ upsert ตารางตรงได้อยู่แล้ว เว็บกรองตอนอ่านด้วย `sanitizeSettings`) เหตุผลที่ไม่ใส่ allowlist ใน SQL: ทุกครั้งที่เพิ่มค่าตั้งค่าใหม่ต้องมี migration ตาม · ตรวจขนาดล่วงหน้าฝั่งเว็บเป็นด่านข้อความ เพดาน 16 KB จริงอยู่ที่ตารางเสมอ
- **แก้แล้ว:** regex ในเทสต์ขอบเขตโค้ดเกษียณถูกทำให้อ่อนลงโดยไม่ตั้งใจตอนเขียนไฟล์ (backslash หาย) แก้ให้ตรงตามที่ตั้งใจ
- **ลำดับงาน (ตามที่ auditor ขอให้จด):** migration ถูกใส่ฐานข้อมูลจริงก่อนผลตรวจนี้ ตามกติกาโหมดอัตโนมัติระดับ 2 (แบบ "เพิ่ม" + dry-run rollback ผ่านก่อน) แล้วจึงรันเทสต์ SQL ทุกไฟล์และตรวจ
