# M2-G: ล็อก bills.last_paid_month (9 พ.ย. 2569)

เจ้าของสั่ง: ต้องแก้ก่อนเชิญผู้ใช้จริง (R15 "ทุกเส้นทาง") · ก่อนแก้: ผู้ใช้เรียก REST PATCH `/bills` ตั้ง `last_paid_month` เป็น "จ่ายแล้ว" โดยไม่มีรายการจ่าย หรือล้างค่าเพื่อจ่ายซ้ำรอบเดิมได้ (ไม่แย่กว่า Dexie แต่ขัดกฎ)

## กติกาใหม่ (`private.bills_guard`, migration `20261108001100`, ใส่ฐานข้อมูลจริงแล้ว)
เปลี่ยน `last_paid_month` ได้เฉพาะ:
1. **จ่ายบิล** (trigger `entries_bill_link` หลังเพิ่มรายการจ่าย) · **ยกเลิกการจ่าย** (trigger `entries_guard` ตอนลบรายการจ่าย) — สองทางนี้ตั้ง `app.bill_paid_path` ครอบคำสั่งอัปเดตเท่านั้น
2. **นำเข้า** (`import_ledger` ตั้ง `app.import_ledger` ก่อนเพิ่มบิล — แก้ลำดับจากเดิมที่ตั้งหลังเพิ่มบิล)
3. **เพิ่มบิลที่มี `last_paid_month`** ได้เมื่อมีรายการจ่าย (`source = recurring`) ที่ผูกกับบิลนั้นและรอบนั้นอยู่จริง — รองรับ "เลิกทำการลบบิล" (ลบบิลไม่ลบรายการจ่าย ใส่บิลกลับได้ด้วยสถานะเดิม) แต่เพิ่มบิลใหม่ที่อ้างว่าจ่ายแล้วโดยไม่มีรายการจ่ายไม่ได้
4. บทบาทระบบ (`postgres`, `supabase_admin`, `service_role`) ซ่อมบำรุงได้
ที่เหลือ (แก้ชื่อ/ยอด/กระเป๋า/เก็บถาวร ฯลฯ) ทำได้ตามปกติ · กฎเดิม (ไม่เกินเดือนปัจจุบัน) ยังอยู่

## ตัดสินใจ
- ตัวแปร `app.*` ตั้งได้เฉพาะในฟังก์ชันของเรา (ผู้ใช้ตั้งผ่าน REST ไม่ได้) และถูกรีเซ็ตทันทีหลังคำสั่งอัปเดต/ท้ายธุรกรรม (`set_config(..., true)`) · ยืนยันด้วยเทสต์ว่าตัวแปรนำเข้าไม่ค้าง (นำเข้าแล้วแก้ตรงๆ ยังถูกปฏิเสธ)
- ไม่ต้องแก้ฝั่งเว็บ: `updateBill` ไม่เคยเขียน `last_paid_month` อยู่แล้ว · ข้อความปฏิเสธเป็นภาษาไทยจากฐานข้อมูล (รหัส 42501) ส่งต่อถึงผู้ใช้ได้
