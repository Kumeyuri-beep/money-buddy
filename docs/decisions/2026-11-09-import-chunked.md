# นำเข้าแบบแบ่งก้อน (9 พ.ย. 2569)

กฎที่แตะ: R1, R15, R16 (ทุกรายการยังผ่าน `private.insert_entry` และทริกเกอร์สมดุลเดิม) · PDPA · แผน `docs/plans/2026-11-09-import-chunked.md`

## สิ่งที่ทำ
- เพดานรวมต่อไฟล์ 10,000 รายการ / 200,000 บรรทัด (เดิม 1,500 / 20,000) · ต่อคำสั่งยังไม่เกิน 1,500 รายการ / 20,000 บรรทัด · ก้อนละ ≤ 500 รายการ / 15,000 บรรทัด (`chunkEntries`, ฟังก์ชันล้วน)
- ไฟล์ที่รายการหรือบรรทัดเกินเพดานต่อคำสั่งใช้ `importChunked`; ที่เหลือใช้ `import_ledger` เดิม (อะตอมมิก)
- migration `20261109000200_import_chunked.sql` (**ยังไม่ได้ใส่ในฐานข้อมูล รออนุมัติ**): `private.import_sessions`, `import_ledger_begin/append/abort/status`, นโยบาย RLS restrictive ล็อกการเขียนทางอื่นขณะเซสชันเปิด, `reset_my_ledger` ล้างเซสชันด้วย · เทสต์ SQL `supabase/tests/import_chunked_test.sql`
- แอป: ก้อนล้ม → สั่งล้างส่วนค้างทันทีแล้วแจ้งผู้ใช้ · ล้างไม่ได้ (เน็ตหลุด/ปิดแท็บ) → `DataSourceGate` ตรวจ `import_ledger_status` ตอนเปิดแอป พาไป `UnfinishedImportPage` (ปุ่มล้าง ไม่ถามรหัสผ่าน) · แถบความคืบหน้า (`<progress>`) ในหน้านำเข้าและหน้าย้ายข้อมูล

## ตัดสินใจ
1. **ไม่อะตอมมิกทั้งไฟล์ ใช้เซสชันครอบแทน**: หลายธุรกรรมจึงมีช่วงข้อมูลครึ่งเดียว เซสชันทำให้ฐานข้อมูลรู้ว่า "ค้าง" แอปจึงไม่ปล่อยเข้าใช้งาน
2. **abort ไม่ถามรหัสผ่านและไม่ติด cooldown 24 ชม.**: ผู้ใช้ใหม่ที่เพิ่งเปลี่ยนรหัสติด cooldown ของ `reset_my_ledger` จะแก้ข้อมูลค้างเองไม่ได้นาน 24 ชม. · ปลอดภัยเพราะเปิดเซสชันได้เฉพาะตอนสมุดว่าง และขณะเซสชันเปิดเขียนทางอื่นไม่ได้ จึงไม่มีข้อมูลจริงให้ abort ลบ
3. **ล็อกการเขียนระหว่างเซสชัน (ผล security-auditor ข้อ 1)**: ไม่งั้นผู้ถือ session ที่ขโมยมาเปิดเซสชันค้างบนสมุดว่างเป็น "ระเบิดเวลา" แล้ว abort ลบข้อมูลจริงที่เจ้าของเพิ่มระหว่างนั้นได้ · อ่านข้อมูลยังได้ตามปกติ
4. ตัวช่วยเซสชันใน `private.*` ใช้ `auth.uid()` ไม่รับรหัสผู้ใช้จากข้างนอก · `advance` ปฏิเสธจำนวน ≤ 0 · `open` ต้องล็อกอิน

## ผลตรวจ
- **money-auditor:** ผ่าน · ลำดับ/ไม่ทิ้ง/ไม่ซ้ำ, R16 ต่อรายการ, R15 บิลก้อนแรก/รายการจ่ายก้อนหลัง (`app.import_ledger` ข้ามการอ่านบิล), เพดานเว็บ=SQL · แก้: ไฟล์ที่รายการไม่ถึง 1,500 แต่บรรทัดเกิน 20,000 ต้องแบ่งก้อนด้วย (มีเทสต์)
- **design-critic:** แก้: ปุ่มล้างเป็นปุ่มแดง + คำเตือนผูก `aria-describedby`, ความคืบหน้าเป็น `<progress>` ไม่ให้ live region อ่านรัว, ข้อความ error ใช้ `role=alert`, บอกว่าออกจากระบบแล้วข้อมูลค้างยังอยู่
- **security-auditor รอบ 1:** เจอข้อ 1 (abort ลบข้อมูลจริงที่เพิ่มระหว่างเซสชันค้างได้) → แก้ตามตัดสินใจข้อ 3-4, `reset_my_ledger` ล้างเซสชัน
- **security-auditor รอบ 2:** ไม่พบทางข้ามผู้ใช้; นโยบาย RLS ไม่ทำให้ฟังก์ชันเดิมพัง (ตอนไม่มีเซสชันผ่านทุกนโยบาย), ผู้ใช้ตั้ง `app.import_ledger` เองไม่ได้ (ต้องไม่เปิด schema private ใน Exposed schemas และไม่ตั้ง pre-request ที่อ่าน header แล้วตั้ง app.*), `reset_my_ledger` ตรงฉบับเดิมทุกด่าน · เจอ **บั๊กไวยากรณ์** `as $` ที่บรรทัด 53 (เกิดจากเครื่องมือแก้ไฟล์ของผมตีความ `$$` เป็น `$`) → แก้แล้ว และตรวจจำนวน `$$` ของทั้งไฟล์ migration/เทสต์ SQL เป็นคู่ · แก้เพิ่ม: `import_session_open` ตรวจสมุดว่างเอง และ `begin` เปิดเซสชันก่อนเขียนข้อมูล + ต้องมีอย่างน้อย 1 บัญชี (กันเซสชันค้างบนสมุดว่างที่ `import_ledger` เดิมยังเขียนทับได้)

## ยังไม่ได้วัด / ความเสี่ยงที่ยอมรับ
- **เวลา `abort` ที่ 10,000 รายการ** (ลบทุกแถวผ่านทริกเกอร์) ยังไม่ได้วัด ถ้าเกินเพดาน ~8 วินาทีผู้ใช้จะติดหน้า "นำเข้าไม่เสร็จ" · วัดหลังใส่ migration แล้วค่อยตัดสิน (ทางเลือก: ลบเป็นชุด/จำกัดบรรทัดรวม)
- เวลา insert ก้อนที่หนักด้านบรรทัด (15,000 บรรทัด/ก้อน) ยังไม่ได้วัด (วัดไว้เฉพาะ 2,000 รายการ = 5.2 วินาที)
- ช่องแข่งขันเล็กน้อย: รายการจริงที่ commit ระหว่างที่ `begin` ตรวจ "สมุดว่าง" กับ commit (create_entry ไม่ถือ advisory lock ของนำเข้า) · ต้องทำพร้อมกันภายในมิลลิวินาที บนสมุดที่เพิ่งว่าง
- ไม่มีปุ่ม "ส่งออกก่อนล้าง" ในหน้าล้างส่วนค้าง เพราะขณะเซสชันเปิดไม่มีข้อมูลจริงของผู้ใช้อยู่ (เขียนทางอื่นไม่ได้)
- ทดสอบหน้าจอ/นำเข้าไฟล์ใหญ่จริงบนเบราว์เซอร์: **เจ้าของต้องลองเอง**
- **ลำดับขึ้นระบบ:** ต้องใส่ migration ก่อน merge/deploy โค้ดนี้ (ด่านเปิดแอปเรียก `import_ledger_status`) · ถ้าลำดับกลับกัน ด่านถือว่า "ไม่ค้าง" ไม่ล็อกใครออก และนำเข้าไฟล์ใหญ่จะล้มพร้อมข้อความ (ไม่มีข้อมูลเสีย)
- ช่องแข่งขันตอน `begin` ยังเปิดอยู่ (security-auditor ข้อ 3, ระดับต่ำ): ระหว่างที่ `begin` ยังไม่ commit แท็บ/อุปกรณ์อื่นของผู้ใช้เองเขียนข้อมูลได้ แล้วถูก abort ลบภายหลัง · ต้องเป็นผู้ใช้คนเดิมเขียนพร้อมกันในช่วงสั้นๆ บนสมุดที่เพิ่งว่าง ไม่ข้ามผู้ใช้ จึงยอมรับ
