# M2-C1: LedgerRepository (8 พ.ย. 2569)

แบ่ง M2-C เป็น 2 PR (1 Ticket = 1 PR ขนาดตรวจได้): **C1 = interface + Dexie + สัญญา + UI ผ่าน context** (PR นี้, refactor ล้วน) · **C2 = SupabaseRepository** ผ่านสัญญาเดียวกัน

## ตัดสินใจ

1. `LedgerRepository` (async, ไม่มีพารามิเตอร์ db) ห่อฟังก์ชันเดิมใน `repository.ts` ไม่แก้ตรรกะเงินแม้แต่บรรทัดเดียว (เสี่ยงต่ำสุด ถ้าพังก็พังที่ call site ซึ่ง tsc จับได้)
2. หน้าจอรับ repository จาก `useRepository()` (ค่าเริ่มต้น = Dexie บน `db` เดิม) · `RepositoryProvider` ไว้สลับเป็น Supabase ใน C2
3. **อยู่นอก interface โดยตั้งใจ:** `migrationSnapshotInfo`/`clearMigrationSnapshot` (App.tsx), local owner (`LocalDataGate`), `setBillPaidMonth` (ไม่มีผู้ใช้ใน UI) — เป็นของเฉพาะ Dexie ที่หายไปใน M2-D
4. `downloadBackup` (ใช้ใน ErrorBoundary ซึ่งอยู่นอก Provider) อ่านผ่าน `defaultLedgerRepository()` · ใน C2 ต้องสลับให้ตรงกับที่ผู้ใช้ล็อกอินอยู่ (จดไว้ ไม่ทำใน C1)
5. เทสต์สัญญา 11 ข้อ รับ factory: C2 เพิ่มแค่ factory ของ Supabase (ต้องมีฐานข้อมูลจริง จึงรันในเครื่องเท่านั้น ไม่รันใน CI ตามกติกา "CI ไม่ใช้ secrets")
6. `repositoryBoundary.test.ts` กัน UI/use case กลับไป import `db` ตรง (ยกเว้นไฟล์ Dexie-only ที่ระบุ)

## ผลตรวจ money-auditor: ผ่าน ไม่มีข้อพบที่ทำให้เงินผิด

เพิ่มเคสในเทสต์สัญญาตามที่ผู้ตรวจชี้ (เฉพาะที่ Dexie ทำได้แล้ว เพื่อบังคับให้ Supabase ทำตาม): รายการบรรทัดเดียว/วันที่ผิด · `MAX_SAFE_INTEGER` พอดี round-trip · ลำดับวันเดียวกัน · จ่ายบิลล้มกลางทางไม่ตั้ง lastPaidMonth · จ่ายบิลวันสิ้นเดือน (dueDay 31 ใน ก.พ.)

**ข้อที่ผู้ตรวจชี้ไว้สำหรับ C2** (ยังไม่ทำใน C1): เคสหลายสกุลเงินไม่สมดุล · ตรวจยอดคงเหลือต่อกระเป๋าหลังแก้/ลบ · เทสต์ 2 repo บนฐานเดียวกันว่าอ่านข้อมูลกันไม่ได้ (factory ต้องรองรับ) · `downloadBackup` ต้องตามผู้ใช้ที่ล็อกอิน · `RepositoryProvider` ยังไม่ถูกใช้ (ค่าเริ่มต้น Dexie ตั้งใจ)
