# ปิดช่องเขียนทับข้ามแท็บของ settings ด้วย compare-and-set (13 พ.ย. 2569)

กฎที่แตะ: R16 (ข้อมูลของผู้ใช้ไม่ถูกเขียนทับเงียบๆ) · ไม่แตะยอดเงิน

## ปัญหา
HANDOFF หัวข้อ 34 backlog ข้อ 1: แผน DCA, ป้ายภาษี และฟอร์มค่าตั้งค่าหน้าบิลส่งค่า "ทั้งก้อน" ของคีย์นั้น แท็บที่บันทึกทีหลังชนะ (เช่น สองแท็บเพิ่มแผนคนละแผนพร้อมกัน แผนหนึ่งหาย) `merge_settings` กันเฉพาะการทับข้ามคีย์ ไม่กันการทับภายในคีย์เดียวกัน

## ตัวเลือก
1. เพิ่ม RPC เติม/ลบทีละรหัส (ต้องมีหลาย RPC ตามชนิดข้อมูล)
2. **(เลือก)** RPC เดียว `merge_settings_if(p_patch, p_remove, p_expect)`: เขียนเมื่อค่าของคีย์ใน `p_expect` ยังเหมือนที่ client อ่านมา ไม่เหมือน = SQLSTATE PT409 · client อ่านใหม่ คำนวณใหม่ ลองซ้ำสูงสุด 5 ครั้ง (พักสั้นๆ แบบสุ่ม)
3. ใช้ `merge_settings` เดิมต่อ: ปิดช่องภายในคีย์ไม่ได้ จึงต้องเพิ่ม migration (ขัดกับที่เจ้าของหวังว่าจะไม่ต้องมี แต่จำเป็น) — เป็น migration แบบ "เพิ่ม" (`create or replace function`) ไม่มี drop

## ผล
- ฟอร์มหน้าบิล: ส่ง baseline (ค่าที่หน้าจอแสดงอยู่) ถ้าคีย์ของฟอร์มเปลี่ยนไปแล้ว = `SettingsConflictError` ไม่เขียนทับและไม่ลองซ้ำ โหลดค่าล่าสุดลงฟอร์มให้ผู้ใช้เห็นก่อนบันทึกอีกครั้ง
- ในเครื่อง (Dexie): ธุรกรรมเดียวอ่าน-คำนวณ-เขียน
- migration 4 ไฟล์ (add-only ทั้งหมด): `...000200_merge_settings_if` (ตัวแรก) · `...000300_..._lock` (ล็อกต่อผู้ใช้ด้วย advisory lock แล้วอ่าน-เทียบ-เขียน) · `...000400_..._conflict_code` (เปลี่ยนรหัสชนจาก 40001 เป็น PT409) · `...000500_..._rowlock` (ตาม security-auditor ระดับกลาง: ล็อกแถวตอนอ่าน for update ให้ทางเขียนอื่นที่แตะแถวเดียวกันรอกัน + จำกัด p_expect ไม่เกิน 20 คีย์)
- **ข้อค้นพบจากเทสต์จริง:** ตอนชนกัน ฟังก์ชันตอบ SQLSTATE 40001 แล้วคำขอของแท็บที่แพ้ค้างราว 60 วินาทีจนหมดเวลาเทสต์ (เห็นว่าฝั่งบริการลองซ้ำรหัสนี้เอง ยังไม่ได้ยืนยันกลไกที่แน่ชัด) เปลี่ยนเป็น PT409 (PostgREST ตอบ HTTP 409) แล้วชนกันตอบทันที เทสต์จริงผ่าน 53/53 · advisory lock คงไว้ (ไม่เป็นโทษ ทำให้ลำดับอ่าน-เทียบ-เขียนของผู้ใช้คนเดียวกันไม่สลับกัน)
- ยอมรับไว้: RPC ไม่มี allowlist คีย์ · เรียก RPC ตรงเก็บได้ถึง 16,383 ไบต์ (เหมือน backlog ข้อ 2-3 เดิม)

## ย้อนกลับ
เว็บเก่าไม่เรียกฟังก์ชันใหม่ ลบฟังก์ชันได้โดยไม่กระทบ (`drop function public.merge_settings_if(jsonb,text[],jsonb)` ต้องให้เจ้าของอนุมัติเพราะเป็น drop)

## ข้อจำกัดที่ยอมรับ (ผลตรวจ security-auditor)
- ตัวเลขใน settings ที่ยาวเกิน 2^53 อาจทำให้เทียบค่าไม่ตรงจนบันทึกไม่ได้ (ข้อมูลไม่ถูกเขียนทับ) · คีย์ที่ใช้อยู่ไม่ถึงขนาดนั้น
- กรณียังไม่มีแถว settings เลย ทางเขียนอื่นที่ไม่ผ่านล็อกยังแย่งสร้างแถวแรกได้ (ผลคือแถวแรกถูกเติมค่าตามคนที่มาก่อน ไม่ข้ามผู้ใช้)
