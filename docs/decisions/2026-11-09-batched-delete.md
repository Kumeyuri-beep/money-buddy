# ล้างข้อมูล/ลบบัญชีแบบเป็นชุด (9 พ.ย. 2569)

กฎที่แตะ: PDPA (สิทธิ์ลบข้อมูล ต้องลบได้จริงแม้ข้อมูลมาก) · ไม่แตะ money-rules · backlog ข้อ 3 ใน HANDOFF

## ปัญหา (วัดจริงบนฐานข้อมูลจริง ในธุรกรรม rollback)
`reset_my_ledger` / `delete_my_account` ลบทั้งก้อนในคำสั่งเดียว: 10,000 รายการ/20,000 บรรทัด = 1.4 วินาที · 10,000 รายการ/200,000 บรรทัด = 10.9 วินาที · role `authenticated` มี `statement_timeout` 8 วินาที → ข้อมูลหนักมากลบไม่สำเร็จ (ผู้ใช้ลบบัญชีตามสิทธิ์ PDPA ไม่ได้) · นำเข้าไฟล์ได้สูงสุด 100,000 บรรทัด (~5.5 วินาที) แต่ข้อมูลที่โตเองไม่มีเพดาน

## ที่ทำ
- migration `20261109000400_batched_delete.sql` (**ยังไม่ได้ใส่ฐานข้อมูล รออนุมัติ**): `reset_my_ledger_step(p_password)` และ `delete_my_account_step(p_password)` คืน `wrong` / `more` / `done` · ลบรายการชุดละ ≤ 500 (บรรทัดลบตาม cascade) · บัญชี/บิล/ตั้งค่า/เซสชันนำเข้าลบในชุดสุดท้าย · ลบบัญชี (`auth.users`) เมื่อรายการหมดเท่านั้น
- แอป: `resetAll` และ `deleteMyAccount` วนเรียกจนได้ `done` (หยุดที่ 200 ชุด) ถามรหัสผ่านครั้งเดียว ถือรหัสในหน่วยความจำระหว่างวนลูป · ค่าที่ไม่รู้จัก (รวม `true` แบบฟังก์ชันเดิม) ไม่นับว่าสำเร็จ
- **ฟังก์ชันเดิมคงไว้ครบ** (เว็บ production ที่ยังไม่อัปเดตเรียกอยู่ และไม่ต้อง `drop`) · ถอดสิทธิ์ของฟังก์ชันเดิมทีหลังเมื่อเว็บใหม่ขึ้นแล้ว

## ตัดสินใจ
1. **ตรวจรหัสผ่านและด่านอื่นทุกชุด ไม่ทำสถานะ "ได้รับอนุญาตแล้ว" ค้างในฐานข้อมูล**: ทางเลือกแบบสองขั้น (ตรวจรหัสครั้งเดียวแล้วเก็บโทเค็นให้เรียกต่อ) ทำให้ผู้ถือ session ที่ขโมยมาลบต่อได้โดยไม่รู้รหัส และต้องมีตาราง/อายุ/ล็อกการเขียนเพิ่ม · แลกกับ bcrypt ต่อชุด (หลักสิบมิลลิวินาที) และต้องถือรหัสในหน่วยความจำของแท็บระหว่างลบ
2. **นับ "ครั้งที่ลอง" เฉพาะรหัสผิด** (เดิมนับทุกครั้งที่เรียก): ไม่งั้นลบ 10,000 รายการ (20 ชุด) ชนเพดาน 5 ครั้ง/15 นาทีเอง · ผลต่อการเดารหัสเท่าเดิม (เดาถูก = จบ, เดาผิด 5 ครั้ง = ถูกล็อก) · ด่านอื่นไม่เปลี่ยน: ล็อกอิน, ไม่ใช่การอ่านอย่างเดียว, เปลี่ยนรหัสแล้ว, cooldown 24 ชม., ล็อก advisory ของผู้ใช้และของการนำเข้า
3. **ล้มกลางทางได้**: ชุดแรกๆ ลบไปแล้วเน็ตหลุด → เหลือสมุดครึ่งเดียว ผู้ใช้สั่งล้าง/ลบซ้ำได้ (ฟังก์ชันทำงานซ้ำได้ ไม่ error เมื่อไม่มีแถวเหลือ) · การลบเป็นสิ่งที่ผู้ใช้ตั้งใจอยู่แล้ว จึงไม่ทำเซสชัน/ย้อนกลับ

## ผลตรวจ security-auditor
ไม่พบช่องที่ผู้ใช้คนหนึ่งลบ/อ่านข้อมูลคนอื่น และไม่พบช่องที่ผู้ถือ session ขโมยแต่ไม่รู้รหัสลบได้แม้ชุดเดียว · ด่านใน `private.deletion_gate` ครบเท่าของเดิม (เพิ่มล็อกการนำเข้าใน delete) · คำขอพร้อมกันถูกจัดคิวด้วย advisory lock ก่อนนับ ลองผิดไม่เกิน 5 ครั้ง · grants/search_path ถูกต้อง · ฝั่งแอปรับเฉพาะ `done`
- **แก้แล้ว (ข้อ 1):** ชุดจำกัดตาม "รายการ ≤ 500" อย่างเดียวเสี่ยงชนเพดานเวลาถ้ารายการมีหลายร้อยบรรทัด → ตัวช่วย `private.delete_entry_batch` จำกัดทั้ง ≤ 500 รายการและบรรทัดสะสม ≤ 20,000 (อย่างน้อย 1 รายการ) ใช้ร่วมกับ `import_ledger_abort` ซึ่งมีจุดอ่อนเดียวกัน (`create or replace` ลายเซ็นเดิม ไม่ต้อง drop)
- **แก้แล้ว (ข้อ 4):** เทสต์ SQL เพิ่ม: ลูปยาว 7 ชุดตัวนับเป็น 0, รหัสผิด 4 ครั้งแล้วรหัสถูกใช้ได้และตัวนับไม่เพิ่ม, ตัวนับใช้ร่วมกับฟังก์ชันเดิม, รายการ system/จ่ายบิลผูกบิล, เปลี่ยนรหัสและเพิกถอน session กลางลูปแล้วถูกปฏิเสธ, ชุดตามบรรทัด (100 รายการ × 300 บรรทัด), ลบบัญชีพร้อมเซสชันนำเข้าค้าง, สิทธิ์ของตัวช่วย private ไม่เปิด PUBLIC
- **แก้แล้ว (ข้อ 5):** ลบบัญชีสำเร็จแต่คำตอบ `done` หาย เรียกซ้ำได้ 42501 → แอปแจ้ง "บัญชีอาจถูกลบแล้ว ลองเข้าสู่ระบบใหม่เพื่อตรวจ" (ไม่นับว่าสำเร็จ)
- **ไม่ทำ (ข้อ 2 ความถูกต้องของข้อมูลระหว่างลบค้าง):** ถ้าลูปหยุดกลางทาง (เน็ตหลุด/ปิดแท็บ) สมุดเหลือครึ่งเดียวและไม่มีตัวบอกว่า "ล้างยังไม่เสร็จ" · การทำสถานะ "กำลังล้าง" ฝั่งเซิร์ฟเวอร์ + ล็อกการเขียน + หน้าให้ใส่รหัสเพื่อทำต่อ เพิ่มตาราง/อายุ/ความซับซ้อนมาก เทียบกับความเสี่ยง: ผู้ใช้ตั้งใจลบอยู่แล้ว สั่งซ้ำได้เสมอ และกรณีที่เกิดคือข้อมูลหนักมากเท่านั้น · ระหว่างลูปแท็บ/อุปกรณ์อื่นยังเพิ่มรายการได้ (ลูปจะวนเพิ่ม มีเพดาน 200 ชุด)
- **ข้อกำหนดการตั้งค่า (ข้อ 3):** PostgREST ต้องไม่ยอมรับ `Prefer: tx=rollback` (ค่าเริ่มต้นของ Supabase `db-tx-end=commit`) ไม่งั้นแถวรหัสผิดถูกย้อนกลับและเดารหัสได้ไม่จำกัด · ช่องนี้มีอยู่แล้วกับฟังก์ชันเดิม ไม่ใช่ของใหม่ · **ผมยืนยันค่านี้ไม่ได้จากเครื่องมือที่มี**
- **ไม่ทำ:** เทสต์ยิงพร้อมกันใน `tests/live` (รหัสผิดพร้อมกัน 10 คำขอ ≤ 5 ครั้ง) เพราะจะล็อกการลบของผู้ใช้ทดสอบ 15 นาทีและกระทบเทสต์อื่นในชุดเดียวกัน

## แก้ประสิทธิภาพตอนใส่ฐานข้อมูลจริง (10 พ.ย. 2569)
- รันเทสต์ SQL บนฐานข้อมูลจริงแล้วพบว่า `private.delete_entry_batch` ฉบับ `delete ... using cte` (คอมมิต a6c36aa) **ค้าง** เมื่อชุดมี 500 รายการ (60 รายการใช้ 0.09 วินาที) เทสต์เดิมในเครื่องมองไม่เห็นเพราะรันบนข้อมูลเล็ก
- แก้: คำนวณรหัสรายการของชุดครั้งเดียวเป็นอาร์เรย์ (`array_agg`) แล้วลบด้วย `id = any(v_ids)` · วัดหลังแก้: ชุด 500 รายการ (รวม bcrypt) = 0.12 วินาที
- ใส่ฐานข้อมูลเป็น 2 ขั้น: `batched_delete` (ฉบับเดิม) แล้ว `batched_delete_fix_perf` (`create or replace` ตัวช่วยตัวเดียว) · ไฟล์ 20261109000400 ใน repo ถูกแก้ให้เป็นสถานะสุดท้ายเท่ากัน
- ผลต่อ production ในช่วงที่ฉบับช้าอยู่บนฐานข้อมูล: `import_ledger_abort` ใช้ตัวช่วยตัวนี้ด้วย (ช่วงสั้นๆ ก่อนแก้)
- เทสต์ SQL ทั้ง 11 ไฟล์ใน `supabase/tests` ขึ้น TESTS_PASSED หลังแก้
