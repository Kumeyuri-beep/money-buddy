# M2-E: PDPA — ยินยอม, นโยบาย, ส่งออกข้อมูล, ลบบัญชี (9 พ.ย. 2569)

## สิ่งที่ทำ
- **หน้ายอมรับนโยบายก่อนใช้ข้อมูล** (`ConsentPage`): หลังเปลี่ยนรหัสผ่านแล้ว ถ้า `profiles.consented_at` ว่าง → เห็นแต่หน้านี้ (สรุป 3 ข้อ + ฉบับเต็มกางอ่านได้ + ติ๊กยอมรับ) · ไม่ยอมรับ = ออกจากระบบ · เวลาตั้งที่เซิร์ฟเวอร์ (`record_consent`) เรียกซ้ำไม่เปลี่ยนเวลาเดิม · **เจ้าของ (kumeyuri) จะเห็นหน้านี้ในการล็อกอินครั้งถัดไป**
- **นโยบายความเป็นส่วนตัว** (`src/domain/privacy/policy.ts` ฉบับ 2026-11-09): ข้อความต้องตรงพฤติกรรมจริง มีเทสต์ตรวจประเด็น (ผู้ดูแลระบบอ่านข้อมูลได้ทางเทคนิค, Supabase/Vercel/Google Fonts, สิงคโปร์/นอกประเทศไทย, สิทธิ์ดาวน์โหลด/ลบ, สำเนาในเบราว์เซอร์ไม่ถูกลบ, บันทึกของผู้ให้บริการ) และเทสต์ห้ามอ้างสิ่งที่ระบบไม่ทำ
- **หน้าโปรไฟล์**: ปุ่ม "ดาวน์โหลดข้อมูลของฉัน" (ไฟล์สำรองจากบัญชีออนไลน์), นโยบายฉบับเต็ม, **ลบบัญชีและข้อมูลทั้งหมด** (ติ๊กรับทราบ + ถามรหัสผ่านในหน้าต่างเดียวกับการล้างข้อมูล → `delete_my_account` จำกัด 5 ครั้ง/15 นาที) แล้วออกจากระบบพร้อมข้อความยืนยันที่หน้าล็อกอิน
- ไม่ต้องมี migration ใหม่: ใช้ `record_consent` / `delete_my_account` ที่มีตั้งแต่ M2-A (ทดสอบ SQL แล้วใน m2a)
- เทสต์จริงใหม่ใน `tests/live` (เจ้าของรัน): ยอมรับนโยบาย (เวลาตั้งที่เซิร์ฟเวอร์ แก้ตรงๆ ไม่ได้), ลบบัญชี (รหัสผิดไม่ลบ, รหัสถูกลบข้อมูลครบทุกตาราง, เข้าสู่ระบบอีกไม่ได้, ผู้ใช้อื่นไม่ถูกแตะ) ด้วยผู้ใช้ทดสอบคนที่ 3

## ตัดสินใจ
1. **บังคับยินยอมที่หน้าจอ ไม่ใช่ RLS** (security-auditor เห็นด้วย): ถ้าบังคับที่ `can_use_data()` จะล็อกการลบบัญชี/บันทึกยินยอมของคนที่ยังไม่ยอมรับ (ขัด PDPA) และถ้าขอยินยอมซ้ำเมื่อนโยบายเปลี่ยน ข้อมูลจะถูกล็อกทันที · ช่องที่ข้อมูลถูกเก็บก่อนยินยอมมีเฉพาะผู้ใช้ที่เรียก API เองหลังเปลี่ยนรหัส (ข้อมูลที่เจ้าตัวส่งเอง) และบันทึกการเข้าสู่ระบบ (ระบุในนโยบายแล้ว)
2. **ไม่เพิ่ม `consented_version`** ตอนนี้ (นโยบายแรก): ข้อความนโยบายบอกตรงๆ ว่ายังไม่บันทึกว่ายอมรับฉบับใด · **backlog:** เพิ่มคอลัมน์ `profiles.consented_version` + `record_consent(p_version)` + เทียบเวอร์ชันใน `gateStateFromProfile` ก่อนแก้นโยบายในสาระสำคัญ
3. **ข้อความนโยบายแก้ตามผลตรวจ**: เพิ่มหัวข้อ "บันทึกการใช้งานของผู้ให้บริการ" (IP/เวลา/คำขอ และบันทึกการเข้าระบบของ Supabase ที่ไม่ถูกลบตามเมื่อลบบัญชี), "จำกัดอัตราการลองเข้าสู่ระบบ + จำกัดรหัสเมื่อลบ/ล้าง" (ไม่ใช่ล็อกบัญชีทั้งหมด), ไม่สัญญาว่าจะขอความยินยอมซ้ำ · ภูมิภาคสิงคโปร์ยืนยันแล้ว (โปรเจกต์ `ap-southeast-1`)
4. **ไม่ลบแถว `auth.audit_log_entries` ใน `delete_my_account`**: ต้องมีสิทธิ์ข้าม schema ของ Supabase และอาจพังได้เมื่อ Supabase เปลี่ยนโครงสร้าง · เปิดเผยในนโยบายแทน

## ⚠ ความเสี่ยงเปิดอยู่ (ต้องให้เจ้าของตัดสินใจ) — ผู้ถือ session ที่ขโมยมาลบบัญชีได้
ที่มา: security-auditor [สูง] · ตอนเปลี่ยนรหัสผ่าน แอปตรวจรหัสเดิมในเบราว์เซอร์เท่านั้น (Supabase `auth.updateUser({password})` ไม่ถามรหัสเดิมจากฝั่งเซิร์ฟเวอร์) คนที่ถือ session ที่ขโมยมาจึงตั้งรหัสใหม่เองได้ แล้วใช้รหัสใหม่ผ่านด่านรหัสผ่านของ `delete_my_account` / `reset_my_ledger` และอาจสั่งออกจากระบบเครื่องอื่นเพื่อล็อกเจ้าของตัวจริงออก · **เป็นความเสี่ยงที่มีมาตั้งแต่ M2-B** (การยึดบัญชีผ่านการเปลี่ยนรหัสมีอยู่ก่อนมีปุ่มลบ) M2-E เพิ่มแค่ปุ่มลบที่ปลายทางเดียวกัน

ทางที่ตรวจแล้ว:
- ตัวเลือก "Secure password change" ของ Supabase ต้องยืนยันซ้ำด้วยรหัส nonce ทางอีเมล/SMS (เราไม่มีอีเมลจริง) และ "เพิ่งล็อกอินใน 24 ชม." ไม่กันผู้ถือ session ที่ขโมยมา → ใช้ไม่ได้ผล
- RPC เปลี่ยนรหัสเองที่ตรวจรหัสเดิม ไม่ช่วย เพราะผู้โจมตียังเรียก endpoint ของ GoTrue ตรงได้
- ลดความเสี่ยงที่ต้นทางคือกัน session ถูกขโมย: **CSP** (backlog เดิม, กัน XSS ซึ่งเป็นทางขโมย token หลัก) และ session ใน localStorage ที่เจ้าของเลือกไว้แล้ว (รับความเสี่ยงนี้ตอน M2-B)
- ตัวเลือกที่ทำได้ถ้าต้องการ: (ก) **cooldown** ให้ `delete_my_account`/`reset_my_ledger` ปฏิเสธถ้ารหัสเพิ่งเปลี่ยนภายใน N ชั่วโมง (ต้องเพิ่ม `profiles.password_changed_at` ที่ตั้งโดย trigger เดิม) — ไม่กันการยึดบัญชีแต่เจ้าของมีเวลาสังเกต/ให้ผู้ดูแลรีเซ็ต (ข) ให้ผู้ดูแลระบบสังเกตการเปลี่ยนรหัสผิดปกติ

**ขอให้เจ้าของเลือก:** ทำ (ก) หรือรับความเสี่ยงไว้จนทำ CSP

## ยังไม่ทำ / ข้อสังเกต
- ช่องทางติดต่อผู้ควบคุมข้อมูลในนโยบายเป็นข้อความกลาง ("ติดต่อผู้ดูแลระบบที่ให้บัญชีแก่คุณ") · **เจ้าของต้องอ่านและรับรองนโยบายก่อนเชิญผู้ใช้จริง** (ร่างนี้ไม่ใช่คำปรึกษากฎหมาย) และตัดสินใจเรื่องช่องทางติดต่อ/ชื่อผู้ควบคุมข้อมูล
- การลบบัญชีไม่ลบสำเนาใน Dexie ของเบราว์เซอร์ (ระบุในนโยบายและหน้าลบแล้ว)
- ทดสอบหน้าจอด้วยเบราว์เซอร์จริง: เจ้าของต้องลองเอง (ผมไม่มีเบราว์เซอร์)
