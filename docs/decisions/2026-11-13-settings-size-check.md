# settings: เพดานขนาดวัดจากข้อความ JSON จริง (13 พ.ย. 2569)

## ที่มา
security-auditor (12 พ.ย. 2569, ตรวจ merge_settings) ชี้ว่า constraint เดิม `settings_value_check` ใช้ `pg_column_size(value) < 16384` ซึ่งวัดขนาด "รูปแบบเก็บภายใน" ไม่ใช่ขนาดข้อมูลที่ผู้ใช้ใส่จริง เจ้าของอนุมัติเมื่อ 13 พ.ย. 2569 ให้เปลี่ยนเป็น `octet_length(value::text)` แม้เป็นการแก้ constraint (migration ที่มี drop ปกติห้ามใส่เอง) โดยมีเงื่อนไข: ตรวจก่อนว่าทุกแถวผ่านขีดใหม่ · dry-run rollback ก่อน · เพิ่มตัวใหม่ก่อนแล้วถอดตัวเก่าในธุรกรรมเดียว · เว็บ production ใช้ได้ปกติ · รันเทสต์ SQL ทุกไฟล์และ live-contract

## ที่ทำ
migration `20261113000100_settings_size_check` (ธุรกรรมเดียว):
1. `add constraint settings_value_size_check check (jsonb_typeof(value) = 'object' and octet_length(value::text) < 16384)` — ตรวจแถวเดิมทุกแถวทันที ถ้ามีแถวเกิน คำสั่งล้มและทั้งธุรกรรมย้อนกลับ (ไม่ถอดตัวเก่า)
2. `drop constraint settings_value_check` — ไม่มีช่วงที่ไม่มี constraint

## ตรวจก่อนใส่ (อ่านอย่างเดียว ไม่ดูเนื้อหา)
- constraint เดิม: `settings_value_check` = `jsonb_typeof(value)='object' and pg_column_size(value) < 16384`
- แถวใน `settings` ณ ตอนตรวจ: 0 แถว · ขนาดข้อความใหญ่สุด 0 ไบต์ · แถวที่เกินขีดใหม่ 0 แถว
- ไม่มีโค้ดใน repo อ้างชื่อ constraint เดิม (ค้น `supabase src tests scripts`)

## ผลต่อผู้ใช้
ไม่มี: ฝั่งเว็บจำกัด 12,000 ไบต์ (`MAX_SETTINGS_BYTES`) ต่ำกว่าขีดใหม่ · `jsonb::text` มีเว้นวรรคหลัง `:` และ `,` จึงใหญ่กว่า JSON แบบกะทัดรัดเล็กน้อย ขีดใหม่ปลอดภัยฝั่งเข้มกว่าเดิมเล็กน้อยเท่านั้น

## ทดสอบ
`supabase/tests/merge_settings_test.sql` เพิ่ม T10b (ขอบ 16,383 ผ่าน / 16,384 ถูกปฏิเสธ, ข้อความซ้ำๆ ขนาดใหญ่ถูกปฏิเสธ) และ T15 (constraint ใหม่ตรวจแล้ว ตัวเก่าถูกถอด ไม่ใช่ object แทรกตรงไม่ได้)

## ย้อนกลับ (ถ้าจำเป็น)
เพิ่ม `settings_value_check` เดิมกลับแล้วถอดตัวใหม่ (migration ย้อนกลับแบบเดียวกัน ตรวจแถวก่อนเช่นกัน)

## ผลตรวจ security-auditor (ไม่พบระดับสูง/กลาง · ไม่มีทางข้ามเพดาน)
- ข้อความของ jsonb ใหญ่กว่าหรือเท่าข้อมูลจริงเสมอ (ตัวควบคุมถูกขยายเป็น `\uXXXX` ตัวเลขยกกำลังสูงถูกขยายเป็นเลขเต็ม) จึงเข้มกว่าเดิมเท่านั้น
- ค่าที่เว็บอนุญาต (12,000 ไบต์ JSON) ไม่มีทางถูกฐานข้อมูลปฏิเสธ: ส่วนต่างสูงสุดของ `jsonb::text` ตามโครงสร้างที่ sanitize ยอมให้มีประมาณ 701 ไบต์ → ใหญ่สุดราว 12,701 ไบต์ ห่างจาก 16,384 ราว 3,600 ไบต์
- ลำดับเพิ่มก่อนถอด: ปลอดภัย (ADD CONSTRAINT ถือล็อกจนจบธุรกรรม และมีสอง constraint พร้อมกันระหว่างสองคำสั่ง)
- ฟังก์ชันที่เขียน settings ทั้งหมด (merge_settings, import_ledger, import_invest) ใช้ได้ตามปกติ · ไม่มีโค้ดอ้างชื่อ constraint เดิม
- **รับข้อต่ำ:** เทสต์ T10b/T15 ต้องยืนยันว่าถูกปฏิเสธด้วย `settings_value_size_check` จริง (แก้แล้ว)
- **ยอมรับ:** ผู้ใช้ที่เรียก RPC ตรงหรือนำเข้าไฟล์ที่แก้มือเก็บได้ถึง 16,383 ไบต์ (เกิน 12,000 ของเว็บ) ผลคือเว็บบันทึกค่าตั้งค่าเพิ่มไม่ได้จนกว่าจะลดขนาด กระทบเฉพาะข้อมูลของคนนั้นเอง · ค่าใหญ่มากที่ส่งมา RPC ต้องถูกแปลงเป็นข้อความก่อนปฏิเสธ (CPU เล็กน้อย ต้องล็อกอิน และ PostgREST จำกัดขนาดคำขอ)
