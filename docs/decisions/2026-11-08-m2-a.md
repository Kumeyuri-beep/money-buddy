# M2-A: ตาราง RLS และ RPC (8 พ.ย. 2569)

แผน `docs/plans/2026-11-08-m2-a-schema.md` · migration `supabase/migrations/` 3 ไฟล์ · เทสต์ `supabase/tests/m2a_schema_test.sql`
ตรวจโดย `security-auditor` + `money-auditor` (8 พ.ย. 2569) แก้ตามผลแล้วในไฟล์ที่ 3

| # | เรื่อง | ตัดสินใจ | เหตุผล / ที่ทำต่อ |
|---|---|---|---|
| 1 | ใส่ลงฐานข้อมูล | ใส่ตรงลงโปรเจกต์ `money-buddy` ที่ยังว่าง (ไม่ใช้ branch DB) แล้วรันเทสต์แบบ rollback | Supabase branching เป็นบริการเสียเงิน (กติกาโหมดทำงานเอง) · โปรเจกต์ว่าง 0 ผู้ใช้ จึงไม่ต้องทำ Snapshot (R6) · เจ้าของอนุมัติการเรียก `apply_migration`/`execute_sql` ทีละครั้ง |
| 2 | trigger บน `auth.users` | **สร้างได้** ผ่าน migration (ผ่านแล้ว) ทั้ง insert (สร้าง profiles) และ update encrypted_password (เคลียร์ธง) | spike ข้อ 6 ของ security-auditor ส่วน "สร้างได้ไหม" ปิดแล้ว · ส่วนพฤติกรรมของ GoTrue จริง (rehash ตอนล็อกอิน, `same_password`, Admin API) ยังต้อง spike ที่ M2-B |
| 3 | `can_use_data()` | ต้องมีแถว profiles + ธง false + **session ใน `auth.sessions` ยังอยู่ + ไม่ใช่ anonymous** | หลัง logout/reset รหัส token เก่าใช้ไม่ได้ทันที (ไม่ต้องรอหมดอายุ) · ยังควรลด JWT expiry ที่ Dashboard เป็น 300-600 วินาที |
| 4 | ข้าม guard ตอนลบบัญชี | **ดู role ของผู้เรียก** (`current_user not in ('authenticated','anon')`) แทนตัวแปร session | ผู้ใช้ผ่าน REST ถูกบังคับเสมอ · การลบ cascade จาก `auth.users` (RPC, Dashboard, Admin API) ทำในนามเจ้าของตารางจึงผ่าน → เจ้าของลบผู้ใช้ตามคำขอ PDPA ได้ (เทสต์ T26) · `service_role` ผ่าน guard ด้วย (เป็นผู้ดูแล) |
| 5 | บรรทัดของ `system`/`recurring` | แก้/ลบ/ย้าย/**เพิ่ม**ตรงๆ ไม่ได้ · เพิ่มได้เฉพาะผ่าน `private.insert_entry` (ตั้ง `app.entry_insert` = id ของรายการที่กำลังสร้าง) | money-auditor A2 · ผู้ใช้ตั้งตัวแปร session เองผ่าน REST ไม่ได้ (PostgREST ตั้งได้แต่ `request.*`) |
| 6 | จ่ายบิลรอบเดียวครั้งเดียว | unique index `(user_id, bill_id, bill_cycle)` บน `entries` | money-auditor A3 · เดิมพึ่ง `bills.last_paid_month` ซึ่งถอยค่าผ่าน REST ตรงได้ |
| 7 | `delete_my_account` | คืน `boolean` · รหัสผิดคืน `false` (ไม่ raise เพื่อให้ตัวนับถูกบันทึก) · ผิด 5 ครั้งใน 15 นาที = ล็อก · ต้องเปลี่ยนรหัสแล้ว | security-auditor #1 · **ข้อจำกัด:** คนถือ token ที่ยังใช้ได้เรียก `auth.updateUser({password})` แล้วลบบัญชีด้วยรหัสใหม่ได้ ด่านจริงคือ session ถูกเพิกถอนเมื่อ reset + JWT สั้น + ผู้ใช้ ≤ 20 คน (ความเสี่ยงที่ยอมรับ) · ถ้าต้องการแข็งขึ้น: บังคับล็อกอินด้วยรหัสผ่านภายใน 5-10 นาที (ตรวจ `amr`) |
| 8 | `record_consent` | ต้องเปลี่ยนรหัสแล้ว | กันคนถือรหัสชั่วคราวกดยินยอมแทน |
| 9 | สิทธิ์เริ่มต้น | `alter default privileges for role postgres`: ตาราง/ลำดับ/ฟังก์ชันใหม่ใน `public` ไม่ให้ `anon`/`authenticated`, ฟังก์ชันใหม่ไม่ให้ PUBLIC execute | migration ถัดไปต้อง `grant` เองเฉพาะที่ต้องใช้ (เทสต์ T28 ตรวจ: RLS ทุกตาราง, anon ไม่มีสิทธิ์, ไม่มี TRUNCATE, ไม่มี Realtime) |
| 10 | schema `private` | **ห้ามเพิ่มใน Exposed schemas ของ API** | ฟังก์ชันใน `private` รับ user id เป็นพารามิเตอร์ (ปลอดภัยเพราะ INVOKER + RLS แต่ไม่ควรเปิด) |
| 11 | คำเตือน advisors | `authenticated_security_definer_function_executable` 2 ข้อ (`delete_my_account`, `record_consent`) | **ตั้งใจ** เป็นฟังก์ชันที่ผู้ใช้ต้องเรียก ตรวจ `auth.uid()` และ `can_use_data()` ภายใน · INFO: บิลไม่มี index FK สำหรับ `wallet_id`/`category_id` (ตารางเล็ก ≤ 20 ผู้ใช้ ยังไม่ทำ) |
| 12 | ชื่อไฟล์ migration | ชื่อไฟล์ใน repo (`20261108000000_…`) ไม่ตรงเลขเวอร์ชันที่ Supabase บันทึกตอน `apply_migration` (ใช้ชื่อ `m2a_schema`, `m2a_rpc_gate`, `m2a_hardening`) | ลำดับตรงกัน · ถ้าใช้ `supabase db push` ภายหลังต้อง `migration repair` ให้เลขตรง |

## ความต่างระหว่างฐานข้อมูลกับโดเมนเว็บ (money-auditor) ที่รับไว้ / ส่งต่อ M2-C, M2-D

| # | ความต่าง | ทางออก |
|---|---|---|
| B1 | DB บังคับ "ผลรวมฝั่งเดบิตต่อสกุลเงิน ≤ 2^53−1"; เว็บ `sumByCurrency` ตรวจผลรวมสะสมตามลำดับบรรทัด Entry ที่หักกลบทีละบรรทัดแต่ผลรวมบวกเกินช่วง (≈ 9×10^13 บาท) เว็บสร้างได้แต่ DB ปฏิเสธ | M2-C: ให้ domain ตรวจผลรวมบวกด้วยเกณฑ์เดียวกัน |
| B2 | ช่วงวันที่: DB 1900-01-01 ถึง 2999-12-31; เว็บ `isValidIsoDate` รับปี 0100-9999 | M2-C: จำกัดฝั่งเว็บให้ตรง |
| B3 | `currency` ต้อง `^[A-Z0-9]{2,10}$`, `memo` ≤ 2000, `groupId` ไม่ว่าง, `sortOrder` เป็นจำนวนเต็ม — เว็บยังไม่ตรวจ | M2-C: เพิ่ม validator ใน domain |
| B4 | เขตเวลา R15: DB ใช้ `Asia/Bangkok`; กฎเขียน "วันที่ของเครื่อง" ผู้ใช้ที่นาฬิกาเครื่องเร็วกว่าไทย (เช่น UTC+9) ช่วง 00:00-02:00 วันที่ 1 ของเดือนจะจ่ายรอบใหม่ไม่ได้ | **ให้เจ้าของพิจารณา** แก้ถ้อยคำ R15 ให้อ้างเวลาเซิร์ฟเวอร์ไทย หรืออนุโลมคลาดเคลื่อน 1 วัน (ผมไม่แก้ `money-rules.md` เอง) |
| B5 | `setup_ledger` ไม่รับบิล; รายการจ่ายบิลที่ผูกลิงก์นำเข้าไม่ได้ถ้าบิลยังไม่มี/`before` ไม่ตรง | M2-D: นำเข้าบิลก่อน (ไม่ตั้ง `last_paid_month`) แล้วนำเข้ารายการจ่ายตามลำดับรอบ หรือนำเข้ารายการโดยไม่ใส่ลิงก์ |
| C | DB หลวมกว่าโดเมน: ไม่ตรวจชนิดบัญชีของ `wallet_id`/`category_id`, ยอดจ่ายเท่ายอดบิล, บิล archived, จ่ายข้ามรอบค้างเก่าสุด, `recurring` ที่ไม่มีลิงก์ลบได้ | ตั้งใจ: กฎเหล่านี้อยู่ที่โดเมนเว็บ (ไม่ port ตารางเวลาบิลไป SQL) · ผู้ใช้เขียนผ่าน REST ตรงกระทบเฉพาะข้อมูลตัวเอง |
| D | errcode `40001` ของ "สถานะบิลเปลี่ยนไปแล้ว" ไคลเอนต์บางตัว retry อัตโนมัติ | M2-C: ตรวจว่า supabase-js ไม่ retry และแปลงเป็นข้อความไทย |
| E | `entries.bill_id` ไม่มี FK ไป `bills` (ลบบิลแล้วรายการจ่ายยังอยู่ ตามโดเมนเดิม) | ตั้งใจ |
| F | ธงบังคับเปลี่ยนรหัสถูกเคลียร์เมื่อ hash เปลี่ยนทุกกรณี รวมเจ้าของรีเซ็ตรหัสชั่วคราว | `reset-password.mjs` ตั้งธง true **หลัง** ตั้งรหัส แล้วอ่านกลับตรวจ (แผน 4.6 ข้อ 6) |

## ผลตรวจซ้ำรอบ 2 (security-auditor) และสิ่งที่แก้ใน migration ที่ 4

| # | เรื่อง | ตัดสินใจ |
|---|---|---|
| 13 | guard ข้ามได้เฉพาะ role ที่ระบุ | `postgres`, `supabase_admin`, `supabase_auth_admin`, `service_role` (เดิมระบุ role ที่ห้าม → role ใหม่ เช่น จาก hook จะข้าม) · **กติกา:** ห้ามใช้ custom access token hook ตั้ง claim `role` หรือให้สิทธิ์จาก `user_metadata` (ผู้ใช้แก้เองได้) |
| 14 | `delete_my_account` กันยิงพร้อมกัน/GET | ปฏิเสธถ้า `transaction_read_only = on` · `pg_advisory_xact_lock` ต่อผู้ใช้ · บันทึกการลองก่อนตรวจรหัสเสมอ · ล้างแถวเก่ากว่า 1 วัน (เทสต์ T24-0) · **ยังไม่ได้ทดสอบกับ PostgREST จริง** (ขึ้นกับรุ่น) → ทดสอบที่ M2-B/M2-E |
| 15 | `can_use_data()` | ตรวจ `not_after` ของ session (เทสต์ T22b) · aal2 ยังไม่บังคับ (ทำตอนเปิด MFA) |
| 16 | รายการ `system` | สร้างได้เฉพาะใน `setup_ledger` (ตัวแปรชั่วคราว `app.setup_ledger`) ทั้งผ่าน RPC และเขียนตรง (เทสต์ T10d) |
| 17 | **ยังไม่พิสูจน์ (สำคัญสุด ทดสอบที่ M2-B)** | GoTrue ลบแถว `auth.sessions` จริงไหมเมื่อ (ก) Admin `updateUserById({password})` (ข) `signOut` แต่ละ scope · เทสต์ T21 ลบแถวเอง ไม่ได้พิสูจน์ข้อนี้ · ถ้าไม่ลบ คนถือ session เก่าเรียก `updateUser({password})` ปลดธงเองได้หลังเจ้าของ reset → `reset-password.mjs` **ต้องลบ session ทั้งหมดของผู้ใช้เอง** แล้วอ่านกลับว่าเหลือ 0 และเปิด "Secure password change" |
| 18 | ยังไม่ทำ (ระดับต่ำ) | เพิ่มเงื่อนไข view ต้อง `security_invoker = true` ใน T28 เมื่อมี view · `profiles.invited_at` กันสมัครเองถ้ามีคนเปิด sign-up ภายหลัง (ตอนนี้พึ่งการปิดที่ Dashboard + เทสต์ M2-F) · ผลข้างเคียงของ `alter default privileges … revoke execute on functions from public` ทุก schema: ฟังก์ชันใหม่ที่ `postgres` สร้าง (ตัวช่วย trigger, auth hook, extension) ต้อง `grant` เอง |
