# M2-D1: นำเข้าไฟล์สำรอง JSON (9 พ.ย. 2569)

แบ่ง M2-D เป็น 2 PR: **D1 = แกนหลักไม่มีหน้าจอ** (PR นี้) · **D2 = หน้าจอย้ายข้อมูล + สลับแอปไปอ่านบัญชีออนไลน์**

## ผลชุดทดสอบจริงของเจ้าของ (9 พ.ย. 2569)
`admin:live-contract` รอบใหม่ผ่าน **21/21** (หลังแก้ rate limit ของชุดทดสอบ และ trigger สมดุลที่ทำให้ลบผู้ใช้ที่มีข้อมูลไม่ได้ ดู 2026-11-09-m2-c2-live-fix.md) · เจ้าของล็อกอินจริง ดาวน์โหลดไฟล์สำรอง (13 บัญชี 3 รายการ) สร้างบัญชี `kumeyuri` เปลี่ยนรหัสและผูกข้อมูลในเครื่องแล้ว ข้อมูลเดิมขึ้นครบ

## กติกาที่เจ้าของสั่ง
**ห้ามลบข้อมูลใน Dexie จนกว่าเจ้าของยืนยันว่านำเข้าครบและยอดตรง** → โค้ดนำเข้าไม่เรียก `resetAll`/`clear`/`delete` กับ Dexie เลย (Dexie ถูกอ่านอย่างเดียวระหว่างย้าย) · มีเทสต์ค้นโค้ดกันไว้ (`importBoundary.test.ts`) · ปุ่มล้างข้อมูลเดิมที่มีอยู่ไม่เปลี่ยน

## สิ่งที่ทำ
1. **`parseBackup(text, today)`** (`src/domain/backup/parseBackup.ts`): ไม่เชื่อไฟล์ — คัดลอกเฉพาะฟิลด์ที่รู้จัก (กัน `__proto__`/ฟิลด์แปลก), ตรวจด้วยกฎเดียวกับตอนบันทึกปกติ (`createEntry`: R1 ช่วงปลอดภัย/ไม่ใช่ข้อความ/ทศนิยม, R16 สมดุลต่อสกุลเงิน; `accountProblem`; `billProblem`; R15 `lastPaidMonth` ไม่เกินเดือนปัจจุบันเวลาไทย; wallet/หมวดต้องมีจริงและชนิดถูก; id ซ้ำ) · เพดาน 20MB / 2,000 บัญชี / 1,500 รายการ / 2,000 บิล / 200 บรรทัดต่อรายการ / 20,000 บรรทัดรวม · ผิดข้อใดข้อหนึ่ง = **ปฏิเสธทั้งไฟล์** รายงานไม่เกิน 30 ข้อ
2. **`import_ledger(p_data)`** (migration `20261108000900`, ใส่ฐานข้อมูลจริงแล้ว): ธุรกรรมเดียว · ปฏิเสธถ้ามีบัญชี/รายการ/บิล/ตั้งค่าอยู่แล้ว (ไม่ทับ ไม่ซ้ำ; นำเข้าซ้ำพร้อมกันกันด้วย advisory lock) · SECURITY INVOKER (RLS ใช้ตามปกติ) · ผิดข้อใด = ย้อนกลับทั้งก้อน · เทสต์ SQL `m2d_import_ledger_test.sql` TESTS_PASSED
3. **รายการจ่ายบิลในไฟล์:** `lastPaidMonth` มาจากไฟล์โดยตรง จึงข้ามการตรวจ "ลำดับรอบ/before" ของ `entries_bill_link` **เฉพาะในธุรกรรมนำเข้า** (GUC `app.import_ledger` ตั้งโดยฟังก์ชันนี้เท่านั้น; เส้นทางจ่ายปกติตรวจเหมือนเดิม ยืนยันด้วยเทสต์ T8) · ข้อมูลเก่าอาจมีห่วงโซ่ `before` ไม่ต่อเนื่อง การบังคับจะทำให้ไฟล์จริงนำเข้าไม่ได้
4. **`LedgerRepository.importBackup`** ทั้ง Dexie และ Supabase ผ่านเทสต์สัญญา 4 ข้อใหม่ (ยอดต่อบัญชีตรง, สถานะบิลคง + ยกเลิกการจ่ายที่นำเข้าได้, ซ้ำ/ทับถูกปฏิเสธ, ข้อมูลเสียไม่เหลือข้อมูลค้าง) + เทสต์จริงที่ส่งข้อมูลเสียเข้า RPC ตรง
5. **`verifyImport`** (`src/app/importVerify.ts`): เทียบต้นทางกับที่อ่านกลับจากออนไลน์ — จำนวน, รหัสครบ, ยอดคงเหลือต่อบัญชี, เนื้อหารายการ (วันที่/หมายเหตุ/ชนิด/บรรทัด), สถานะบิล · ให้หน้าจอ D2 แสดงตารางยอดให้เจ้าของเห็นก่อนยืนยัน

## แผน D2 (ยังไม่ทำ)
ขั้นตอนบังคับ: (1) ดาวน์โหลดไฟล์สำรองก่อนเสมอ (ปุ่มนำเข้าเปิดหลังกดดาวน์โหลดแล้ว) (2) อ่าน Dexie → `parseBackup` → แสดงสรุป (3) ยืนยัน → `importBackup` (4) อ่านกลับ → `verifyImport` แสดงตารางยอดต่อบัญชี (5) เจ้าของกดยืนยัน "ยอดตรง" แล้วจึงสลับแอปไปใช้บัญชีออนไลน์ · กฎเลือกแหล่งข้อมูล: ออนไลน์ไม่ว่าง → ใช้ออนไลน์; ออนไลน์ว่างและมีข้อมูลในเครื่อง → หน้าย้ายข้อมูล; ว่างทั้งคู่ → ตั้งต้นออนไลน์ · Dexie คงไว้ตลอด ไม่ลบโดยโค้ด · ต้องแก้ด้วย: `downloadBackup` (ErrorBoundary) ตามผู้ใช้ที่ล็อกอิน, ช่องกรอกรหัสผ่านตอนล้างข้อมูล, `LocalDataGate` ไม่ขวางผู้ใช้อื่นที่ใช้ออนไลน์, ส่ง `today` เวลาไทยให้ `payBill`

## หมายเหตุสำหรับ M2-G (ล็อก `bills.last_paid_month`)
ต้องยอมให้ `import_ledger` เขียนค่านี้ได้ (เช็ก `app.import_ledger = 'on'`) และเส้นทางจ่าย/ยกเลิก (trigger เดิม)
