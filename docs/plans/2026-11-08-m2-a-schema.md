## 2. การออกแบบสำคัญ

- **ธงบังคับเปลี่ยนรหัส (ปิดไว้ก่อน):** trigger สร้าง `profiles` ให้ผู้ใช้ใหม่ทุกคนด้วยธง true · `private.can_use_data()` ผ่านเมื่อมีแถวและธงเป็น false เท่านั้น · policy `RESTRICTIVE` บนตารางข้อมูลทุกตาราง · trigger เคลียร์ธงเฉพาะเมื่อ hash รหัสผ่านเปลี่ยนจริง · ผู้ใช้เขียน `profiles` ไม่ได้
- **R16 ที่ตาราง:** constraint trigger แบบ deferred ตรวจ ≥ 2 บรรทัด, ผลรวมต่อสกุลเงิน = 0, ผลรวมฝั่งเดบิตไม่เกิน 2^53−1 (ทำให้ผลรวมระหว่างทางไม่เกินช่วงปลอดภัยของ JavaScript ไม่ว่าเรียงบรรทัดอย่างไร) · `amount` เป็น bigint `<> 0` และอยู่ในช่วง ±(2^53−1) (R1)
- **R15 ที่ตาราง (ไม่ใช่แค่ใน RPC):** รายการ `system` แก้/ลบไม่ได้ · `recurring` แก้ไม่ได้ · เพิ่มรายการที่ผูกบิล = ตรวจ `before` ตรงกับ `lastPaidMonth` ปัจจุบัน, รอบต้องใหม่กว่า, ไม่เกินเดือนปัจจุบัน (เวลาไทย) แล้วตั้ง `lastPaidMonth` ในธุรกรรมเดียว · ลบรายการจ่ายบิล = คืน `lastPaidMonth` เป็น `before` ในธุรกรรมเดียว เฉพาะรอบล่าสุด · `bills.last_paid_month` เกินเดือนปัจจุบันไม่ได้
- **RPC เป็น SECURITY INVOKER** (RLS และ trigger มีผลเต็ม): `create_entry`, `update_entry`, `setup_ledger` รับ jsonb รูปแบบเดียวกับ `Entry` ฝั่งเว็บ · ยกเว้น DEFINER 2 ตัว `record_consent` (ตั้ง `consented_at` ฝั่งเซิร์ฟเวอร์) และ `delete_my_account(password)` (ตรวจธงและรหัสผ่านฝั่งเซิร์ฟเวอร์ ลบ `auth.users` แล้ว cascade ทุกตาราง)
- **สิทธิ์:** `anon` ไม่มีสิทธิ์ใดๆ · `authenticated` ไม่มี TRUNCATE · ฟังก์ชันภายในอยู่ schema `private` ไม่เปิดผ่าน API · ทุกฟังก์ชัน `search_path = ''`
- **ไม่ลบบัญชีที่มีรายการ** (FK `NO ACTION`) ใช้ `archived` แทน ตรงกับโค้ดเดิม

## 3. ข้อจำกัดที่รู้

- การเพิ่มบรรทัดใหม่เข้ารายการ `system`/`recurring` ที่มีอยู่แล้วด้วยการ INSERT ตรงๆ (บรรทัดคู่สมดุล) ยังทำได้ เพราะแยกไม่ได้ว่ารายการถูกสร้างในธุรกรรมเดียวกันหรือไม่ (กระทบเฉพาะข้อมูลของเจ้าตัวเอง) · UPDATE/DELETE บรรทัดถูกกันแล้ว
- ลำดับ "จ่ายรอบเก่าสุดที่ค้างก่อน" ยังบังคับที่โดเมนฝั่งเว็บ ฐานข้อมูลบังคับเพียงว่ารอบต้องใหม่กว่า `lastPaidMonth` และไม่เกินเดือนปัจจุบัน (ไม่ port ตารางเวลาบิลไปเป็น SQL เพื่อไม่ให้สองที่ขัดกัน)
- วันที่ "เดือนปัจจุบัน" ฝั่งเซิร์ฟเวอร์ใช้เขตเวลา `Asia/Bangkok` ฝั่งเว็บใช้วันที่ของเครื่อง อาจต่างกันช่วงคาบเกี่ยวเที่ยงคืนสิ้นเดือน (ผู้ใช้อยู่ในไทย)

## 4. ที่ยังทำไม่ได้ และเหตุผล

- ใส่ migration ลงโปรเจกต์ `money-buddy` ผ่านเครื่องมือ Supabase ถูกระบบอนุญาตของ Claude Code ปฏิเสธ จึงยังไม่ได้ใส่และยังไม่ได้รันเทสต์ SQL (ไม่เลี่ยงด้วยทางอื่น)
- แผนเดิมให้ทดลองบน branch DB (`create_branch`) แต่ Supabase branching เป็นบริการเสียเงิน (กติกาโหมดทำงานเอง: ใช้เงินต้องถามเจ้าของ) · โปรเจกต์ยังว่าง (0 ตาราง 0 ผู้ใช้) จึงเสนอใส่ตรงแล้วรันเทสต์ rollback · ถ้าพังแก้ด้วย migration ถัดไปหรือรีเซ็ตโปรเจกต์ได้ (ไม่มีข้อมูลจริง)
