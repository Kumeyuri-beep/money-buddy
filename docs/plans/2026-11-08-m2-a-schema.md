## 2. การออกแบบสำคัญ

- **ธงบังคับเปลี่ยนรหัส (ปิดไว้ก่อน):** trigger สร้าง `profiles` ให้ผู้ใช้ใหม่ทุกคนด้วยธง true · `private.can_use_data()` ผ่านเมื่อมีแถว ธงเป็น false **session ยังอยู่ใน `auth.sessions` และไม่ใช่ anonymous** · policy `RESTRICTIVE` บนตารางข้อมูลทุกตาราง · trigger เคลียร์ธงเฉพาะเมื่อ hash รหัสผ่านเปลี่ยนจริง · ผู้ใช้เขียน `profiles` ไม่ได้
- **R16 ที่ตาราง:** constraint trigger แบบ deferred ตรวจ ≥ 2 บรรทัด, ผลรวมต่อสกุลเงิน = 0, ผลรวมฝั่งเดบิต ≤ 2^53−1 · `amount` เป็น bigint `<> 0` ในช่วง ±(2^53−1) (R1)
- **R15 ที่ตาราง (ไม่ใช่แค่ใน RPC):** `system` แก้/ลบไม่ได้ · `recurring` แก้ไม่ได้ · เพิ่มรายการที่ผูกบิลตรวจ `before` ตรงกับ `lastPaidMonth` ปัจจุบัน รอบใหม่กว่า ไม่เกินเดือนปัจจุบัน (เวลาไทย) แล้วตั้ง `lastPaidMonth` ในธุรกรรมเดียว · ลบรายการจ่ายบิล = คืน `lastPaidMonth` เฉพาะรอบล่าสุด · unique `(user_id, bill_id, bill_cycle)` · บรรทัดของ `system`/`recurring` เพิ่ม/แก้/ย้าย/ลบตรงๆ ไม่ได้
- **RPC เป็น SECURITY INVOKER** (RLS และ trigger มีผลเต็ม): `create_entry`, `update_entry`, `setup_ledger` รับ jsonb รูปแบบเดียวกับ `Entry` ฝั่งเว็บ · DEFINER 2 ตัว: `record_consent`, `delete_my_account(password)` (คืน boolean, ล็อกหลังผิด 5 ครั้งใน 15 นาที)
- **สิทธิ์:** `anon` ไม่มีสิทธิ์ใดๆ · `authenticated` ไม่มี TRUNCATE · ฟังก์ชันภายในอยู่ schema `private` (ห้ามเปิดใน Exposed schemas) · ทุกฟังก์ชัน `search_path = ''` · สิทธิ์เริ่มต้นของตาราง/ฟังก์ชันใหม่ถูกถอนแล้ว
- **ไม่ลบบัญชีที่มีรายการ** (FK `NO ACTION`) ใช้ `archived` แทน ตรงกับโค้ดเดิม

## 3. ข้อจำกัดที่รู้

- ลำดับ "จ่ายรอบเก่าสุดที่ค้างก่อน" ยังบังคับที่โดเมนฝั่งเว็บ ฐานข้อมูลบังคับเพียงว่ารอบต้องใหม่กว่า `lastPaidMonth` และไม่เกินเดือนปัจจุบัน (ไม่ port ตารางเวลาบิลไปเป็น SQL เพื่อไม่ให้สองที่ขัดกัน)
- เขตเวลา "เดือนปัจจุบัน" ฝั่งเซิร์ฟเวอร์ใช้ `Asia/Bangkok` ฝั่งเว็บใช้วันที่ของเครื่อง (ดู decisions ข้อ B4 — รอเจ้าของพิจารณา)
- `delete_my_account`: คนถือ token ที่ยังใช้ได้เปลี่ยนรหัสเองแล้วลบได้ (ความเสี่ยงที่ยอมรับ ด่านจริงคือ session ถูกเพิกถอนตอน reset + JWT สั้น)

## 4. ผลการทำจริง

- ใส่ผ่านเครื่องมือ Supabase ทีละ migration (เจ้าของกดอนุมัติเอง) ลงโปรเจกต์ที่ยังว่าง · **trigger บน `auth.users` สร้างได้** · ไม่ใช้ branch DB (เป็นบริการเสียเงิน)
- เทสต์ SQL ผ่านครบ แล้ว rollback (ตรวจแล้ว 0 ผู้ใช้/ข้อมูลหลังรัน)
- `get_advisors` security: ไม่มี error · WARN 2 ข้อที่ตั้งใจ (`delete_my_account`, `record_consent` เป็น SECURITY DEFINER ที่ผู้ใช้ต้องเรียก) · performance: INFO (index FK ของ `bills`)
- ผู้ตรวจ: `security-auditor` + `money-auditor` → แก้ในไฟล์ที่ 3 และ 4
- ข้อควรระวัง: การใช้ `String.replace` ใน JavaScript กับข้อความที่มี `$$` ทำให้ `$$` กลายเป็น `$` (เคยทำไฟล์เทสต์เสียครั้งหนึ่ง และถูกจับได้ตอนตรวจ) ให้ใช้ฟังก์ชันเป็นตัวแทนที่

## 5. ขั้นถัดไป

1. เจ้าของ: ลด JWT expiry เป็น 300-600 วินาที · ตรวจว่า Anonymous sign-ins, Phone, provider อื่นปิด · "Allow new users to sign up" ปิด
2. spike ที่ M2-B กับผู้ใช้ที่สร้างผ่าน Admin API จริง: ธงเป็น true หลังสร้าง · ล็อกอินด้วยรหัสชั่วคราวแล้วธงยังเป็น true · `updateUser` ด้วยรหัสเดิมถูกปฏิเสธ · Admin `updateUserById({password})` เพิกถอน session เดิมหรือไม่
3. ก่อน M2-C: ตรวจเกณฑ์ผลรวมฝั่งเดบิต ช่วงวันที่ และ validator ฝั่งโดเมนให้ตรง DB (decisions ข้อ B1-B3)
