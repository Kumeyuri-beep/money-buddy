# แผนสั้น: เพิ่ม/ซ่อนหมวดรายรับ-รายจ่าย (ฟีดแบ็กใช้งานจริง ข้อ 2 · 14 พ.ย. 2569)

เจ้าของสั่ง: เพิ่มหมวดใหม่ได้ · ซ่อนหมวดที่ไม่ใช้ (ห้ามลบจริง เพราะรายการเก่ายังอ้างถึง) · หมวดที่ซ่อนไม่แสดงในฟอร์มแต่รายการเก่ายังเห็นชื่อเดิม เปิดกลับได้ · ห้ามชื่อว่าง/ซ้ำ · หมวดผลการลงทุนที่ระบบสร้างห้ามซ่อน/แก้ · อยู่ในไฟล์สำรองและนำเข้ากลับได้ · สิทธิ์ UPDATE ของ accounts เหลือแค่ name (#125) จึงซ่อนผ่าน RPC ที่ตรวจเจ้าของ

## ออกแบบ
- ใช้คอลัมน์ `accounts.archived` ที่มีอยู่แล้ว (ฟอร์มกรอง archived อยู่แล้ว · parseBackup/importVerify/import RPC รองรับอยู่แล้ว) จึง **ไม่เปลี่ยนโครงสร้างตาราง**
- migration แบบ "เพิ่ม" ตัวเดียว: `public.set_category_archived(p_id, p_archived)` (security definer แคบสุด: เขียนเฉพาะ archived ของแถว auth.uid() ตัวเอง · เฉพาะ income/expense · ห้าม inv-* · ต้องเหลือหมวดบาทที่ใช้งานอย่างน้อย 1 ต่อประเภท · ล็อกแถวกันสองแท็บ · ด่าน can_use_data)
- เพิ่มหมวด = insert accounts (สิทธิ์เดิมอนุญาต) ผ่าน `addCategory` · ตรวจชื่อ (ว่าง/ยาว/อักขระมองไม่เห็น/ซ้ำประเภทเดียวกันรวมที่ซ่อน/ชื่อหมวดระบบ) ในโดเมน `checkCategoryAdd`/`checkCategoryHide` ใช้ร่วม Dexie+Supabase
- ช่องโหว่ที่ต้องปิดระหว่างทำ: แก้รายการเก่าในหมวดที่ซ่อน → ฟอร์มต้องคงหมวดเดิม (`counterOptions(..., keepId)`/`buildEntry({keepCounterId})`) · ตัวกรองรายการ/แก้บิลต้องเห็นหมวดที่ซ่อน (ป้าย "ซ่อนอยู่")
- UI: จัดการในการ์ด "ชื่อหมวดรายรับ-รายจ่าย" (โปรไฟล์): ปุ่มซ่อน · ช่องเพิ่มหมวด · ส่วน "หมวดที่ซ่อนอยู่" + เปิดกลับ

## ลำดับทำงาน (กติกาโหมดอัตโนมัติ 2)
เทสต์ก่อน → dry-run migration แบบ rollback → ใส่ฐานข้อมูล (ก่อน merge เว็บ) → เทสต์ SQL ใหม่ TESTS_PASSED → โค้ด → npm test/typecheck/build/e2e → security-auditor + money-auditor + design-critic → live-contract บน branch → PR → merge → live-contract บน main
