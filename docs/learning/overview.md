# Money Buddy: ภาพรวมโปรเจกต์ (เขียนให้เจ้าของอ่าน)

เอกสารนี้อธิบายแบบภาษาคน ไม่ต้องรู้โค้ด อ่านจบแล้วควรตอบได้ว่า "ข้อมูลของฉันไปไหน ใครเห็น และถ้าอยากเพิ่มฟีเจอร์ต้องทำอะไร" (ข้อมูลตัวเลขในเอกสารนี้เป็นตัวอย่างสมมติทั้งหมด)

---

## 1. โปรเจกต์นี้คืออะไร

แอปเว็บจัดการเงินส่วนตัวภาษาไทย: จดรายรับรายจ่าย ดูกระเป๋าเงิน บิลประจำ พอร์ตลงทุน แผนเกษียณ คำนวณภาษี สแกนสลิป เปิดได้ทั้งบนคอมและมือถือ (เพิ่มลงหน้าจอโฮมได้)

หลักใหญ่ 3 ข้อ (อยู่ใน `CLAUDE.md` และ `docs/money-rules.md`):
1. **เงินเก็บเป็น "สตางค์" จำนวนเต็มเสมอ** (฿12.34 = 1234) ไม่ใช้ทศนิยมเพราะคำนวณผิดเพี้ยนได้
2. **ระบบบัญชีคู่:** ทุกเหตุการณ์ทางเงินคือ "รายการ" ที่มีอย่างน้อย 2 บรรทัด และผลรวมต้องเป็นศูนย์ (เงินออกจากที่หนึ่ง = เงินเข้าอีกที่หนึ่ง) ยอดคงเหลือ **คำนวณ** จากบรรทัดเหล่านี้ ไม่เคยเก็บแยก จึงไม่มีวัน "ยอดไม่ตรง"
3. **ข้อมูลเป็นของผู้ใช้:** ดาวน์โหลดทั้งหมดเป็นไฟล์สำรองได้เสมอ และลบบัญชีพร้อมข้อมูลได้เอง

## 2. แผนที่โฟลเดอร์ (ไล่จากข้างในออกข้างนอก)

| โฟลเดอร์ | ทำอะไร | ข้อห้ามสำคัญ |
|---|---|---|
| `src/domain/` | "สมอง" ของระบบ: สูตรเงิน บัญชีคู่ ภาษี เกษียณ การลงทุน กฎต่างๆ | ไม่แตะหน้าจอ ไม่แตะฐานข้อมูล ไม่แตะอินเทอร์เน็ต |
| `src/app/` | "ขั้นตอนการใช้งาน" ต่อสิ่งของเข้าด้วยกัน เช่น ตั้งต้นบัญชี แปลงข้อความฟอร์มเป็นยอดเงิน | ไม่แตะ React |
| `src/storage/` | "คนคุยกับฐานข้อมูล" (`supabaseRepository.ts` ออนไลน์ · `repository.ts` เก็บในเบราว์เซอร์แบบเดิม) | เขียนข้อมูลผ่านจุดเดียวนี้เท่านั้น |
| `src/ui/` | หน้าจอ (React) | **ห้ามมีสูตรเงิน** ให้เรียก domain เท่านั้น |
| `supabase/migrations/` | คำสั่งเปลี่ยนโครงสร้างฐานข้อมูลทีละไฟล์ (เรียงตามวันที่) | ห้ามแก้ไฟล์ที่ใส่ไปแล้ว ให้เพิ่มไฟล์ใหม่ |
| `supabase/tests/` | เทสต์ที่รันในฐานข้อมูลจริง (ผ่านเมื่อเห็น `TESTS_PASSED`) | |
| `tests/unit/` | เทสต์อัตโนมัติ (Vitest) · `tests/live/` เทสต์กับ Supabase จริง · `tests/e2e/` เทสต์หน้าจอ (Playwright) | |
| `docs/` | `money-rules.md` กฎเหล็ก · `decisions/` เหตุผลการตัดสินใจ · `learning/` บันทึกสำหรับเจ้าของ · `HANDOFF.md` สถานะงานล่าสุด | |

ทำไมแยกชั้น: ถ้าสูตรเงินอยู่แต่ใน `domain` ก็ทดสอบได้ละเอียดโดยไม่ต้องเปิดหน้าจอหรือฐานข้อมูล และหน้าจอเปลี่ยนหน้าตาได้โดยไม่กระทบตัวเลข

## 3. ข้อมูลไหลจากหน้าเว็บถึงฐานข้อมูลอย่างไร

ตัวอย่าง: คุณกดบันทึก "ข้าวมันไก่ 65 บาท"

1. **หน้าจอ (`ui`)** รับข้อความที่พิมพ์ ส่งต่อให้ชั้นถัดไป
2. **ขั้นตอน (`app`)** แปลง "65" เป็น **6500 สตางค์** (ที่เดียวที่แปลงเข้า ตามกฎ R2) และสร้างรายการ 2 บรรทัด: รายจ่าย +6500 / กระเป๋า −6500
3. **สมอง (`domain`)** ตรวจกฎ: อย่างน้อย 2 บรรทัด ผลรวมเป็น 0 ไม่มีบรรทัดยอด 0 วันที่มีจริง ฯลฯ ถ้าผิดจะแจ้งเป็นภาษาไทยตั้งแต่ตรงนี้
4. **คนคุยฐานข้อมูล (`storage`)** เรียกฟังก์ชันของฐานข้อมูล (`create_entry`) ผ่านอินเทอร์เน็ตพร้อมตั๋วล็อกอินของคุณ
5. **ฐานข้อมูล (Supabase/Postgres)** ตรวจ **ซ้ำอีกรอบ** ด้วยกฎของตัวเอง (สมดุล, ผูกกับเจ้าของข้อมูล, ห้ามแก้ยอดยกมา ฯลฯ) แล้วเขียนทั้งรายการในธุรกรรมเดียว: สำเร็จครบหรือไม่เขียนเลย
6. กลับมาที่หน้าจอ โหลดข้อมูลใหม่แล้วคำนวณยอดแสดงผลจากบรรทัดทั้งหมด

ที่น่ารู้:
- **ตรวจสองที่โดยตั้งใจ** (โค้ดฝั่งเว็บ + ฐานข้อมูล): เว็บตรวจเพื่อให้ผู้ใช้ได้ข้อความดีๆ ฐานข้อมูลตรวจเพราะ "เชื่อเว็บไม่ได้" (ใครก็ยิงคำขอตรงๆ ข้ามหน้าเว็บได้)
- **ตั้งค่า** (วันเงินเดือน เป้า ฯลฯ) เขียนแบบ "เทียบค่าเดิมก่อนทับ" กันสองแท็บเขียนชนกัน
- **ข้อมูลในเครื่อง (Dexie/IndexedDB)** เป็นระบบเดิมสมัยก่อนออนไลน์ ยังเก็บไว้จนกว่าจะย้ายเสร็จ (ดู `docs/decisions/2026-11-04-m2-auth.md`)
- **สแกนสลิป (OCR)** ทำในเบราว์เซอร์ของคุณทั้งหมด รูปสลิปไม่ถูกส่งออกไปไหน ไฟล์ตัวอ่านมาจากเว็บเราเองไม่ใช่ CDN

## 4. ความปลอดภัยมีกี่ชั้น

สรุป **7 ชั้น** (ไล่จากด่านแรกที่ผู้ใช้เจอ):

1. **ล็อกอินด้วยชื่อผู้ใช้+รหัสผ่าน** ไม่สมัครเองจากเว็บ (เจ้าของสร้างบัญชีให้) · รหัสชั่วคราวต้องเปลี่ยนก่อนใช้งาน · หลังเปลี่ยนรหัสมีช่วงรอ 24 ชั่วโมงก่อนล้างข้อมูล/ลบบัญชี · ออกจากระบบอุปกรณ์อื่นได้
2. **RLS (Row Level Security)** ฐานข้อมูลบังคับเองว่า "แถวนี้เป็นของใคร" ผู้ใช้เห็น/แก้ได้เฉพาะแถวของตัวเอง ต่อให้ยิงคำขอตรงๆ ก็เห็นของคนอื่นไม่ได้ (มีเทสต์จริงกับ Supabase ยืนยัน)
3. **กฎในฐานข้อมูล** ข้อจำกัด (constraint) + trigger: รายการต้องสมดุล ยอดยกมาแก้ไม่ได้ ซื้อขายผิดลำดับ/ขายเกินไม่ได้ ผู้ใช้แก้ชื่อบัญชีได้เฉพาะคอลัมน์ `name` (สิทธิ์ระดับคอลัมน์)
4. **ทางเข้าที่ควบคุม** เขียนข้อมูลสำคัญผ่านฟังก์ชัน (RPC) ที่ตรวจกฎเสมอ แทนการเขียนตารางตรงๆ · ผู้ที่ยังไม่เปลี่ยนรหัสหรือ session หมดอายุ ใช้ข้อมูลไม่ได้ทันที
5. **ส่วนหัวความปลอดภัยของเว็บ (CSP ฯลฯ)** ห้ามรันสคริปต์แปลกปลอม ห้ามติดต่อออกนอกเว็บเรากับ Supabase ของเราเท่านั้น ห้ามอยู่ใน iframe ของเว็บอื่น (กันการขโมย session)
6. **กุญแจผู้ดูแล (service_role) อยู่นอกโปรเจกต์** ในไฟล์ในเครื่องคุณ ไม่เข้า git ไม่เข้าเว็บ มีเทสต์สแกนว่าโค้ดที่ build ออกมาไม่มีกุญแจระดับผู้ดูแล · สคริปต์ผู้ดูแล (สร้าง/รีเซ็ต/ลบผู้ใช้) คุณรันเองเท่านั้น ผู้ช่วย AI ถูกห้าม
7. **ด่านกันพลาดของกระบวนการทำงาน** ทำเป็น PR ทีละเรื่อง · CI (`test` + `e2e`) ต้องผ่านก่อน merge · ผู้ตรวจเฉพาะทาง (money-auditor, security-auditor, design-critic) · ห้ามใส่ migration ที่ลบ/แก้ชนิดข้อมูลเองโดยไม่ถามคุณ · ห้าม push `main`/force push · ก่อนลบผู้ใช้ต้องพิมพ์ชื่อซ้ำ

**ข้อจำกัดที่ต้องรู้ตรงๆ:** ผู้ดูแลระบบ (เจ้าของโปรเจกต์ Supabase) อ่านข้อมูลทุกคนได้ทางเทคนิค (บอกไว้ในนโยบายความเป็นส่วนตัวแล้ว) · ระบบ **ไม่มีสำรองข้อมูลบนเซิร์ฟเวอร์** ให้ผู้ใช้ดาวน์โหลดไฟล์สำรองเอง (มีแถบเตือนทุก 7 วัน) · เคยเกิดเหตุลบผู้ใช้ทั้งหมดโดยไม่ตั้งใจ (HANDOFF หัวข้อ 43) จึงมีสคริปต์ลบทีละคน

## 5. ถ้าจะเพิ่มฟีเจอร์ ต้องทำอะไรบ้าง

ลำดับที่ทำจริงในโปรเจกต์นี้ (ทีละ Ticket / ทีละ PR):

1. **ตั้งโจทย์และอ่านกฎ** อ่าน `docs/money-rules.md` ถ้าแตะเงิน · ถ้ากฎขัดกันหรือไม่ชัด ให้หยุดถามเจ้าของ (ห้ามแก้กฎเอง) · ฟีเจอร์ใหญ่เขียนแผนสั้นใน `docs/plans/`
2. **เขียนเทสต์ก่อน** (`tests/unit/`): สูตรเงินต้องมีเทสต์ขอบเขต ยอด 0 ยอดน้อยมาก วันสิ้นเดือน
3. **เขียนสูตร/กฎใน `src/domain/`** (เงินเป็นสตางค์จำนวนเต็ม ปัดเศษตามกฎ ไม่ใช้ float)
4. **ต่อขั้นตอนใน `src/app/`** (แปลงข้อความฟอร์ม ↔ สตางค์ที่นี่)
5. **ถ้าต้องเก็บข้อมูลใหม่:**
   - ข้อมูลหลายตาราง/ใหม่ → เพิ่มไฟล์ใน `supabase/migrations/` (ตารางใหม่ต้องเปิด RLS และมี policy ผูก `user_id`; เพิ่มเทสต์ SQL ใน `supabase/tests/` ให้จบด้วย `TESTS_PASSED`; ถ้ามี `drop`/`delete`/เปลี่ยนชนิดคอลัมน์ **ต้องรอคุณอนุมัติ** ผมใส่เองไม่ได้)
   - แค่ค่าตั้งค่าเล็กๆ → เพิ่มคีย์ใน `FinanceSettings` (`src/domain/bills/settings.ts` + `settingsPatch.ts`) ไม่ต้อง migration
   - เพิ่มเมธอดใน `LedgerRepository` แล้วทำทั้ง 2 ที่เก็บ (เครื่อง + ออนไลน์) ให้ผ่าน **เทสต์สัญญาชุดเดียวกัน** (`tests/unit/repositoryContract.ts`) และเพิ่มเทสต์ live ถ้าแตะฐานข้อมูลจริง
6. **ทำหน้าจอใน `src/ui/`** เรียก domain/app เท่านั้น · ตามดีไซน์ Aurora Glass (กระจกเฉพาะการ์ดสรุป ตารางใช้พื้นทึบ) · ตัวหนังสือต้องผ่าน WCAG AA · ใช้คีย์บอร์ดได้ · รองรับ 360px (ปุ่ม 44px)
7. **ตรวจ:** `npm test` + `npm run typecheck` + `npm run build` · ให้ผู้ตรวจที่เกี่ยวข้อง (แตะเงิน → money-auditor · แตะหน้าจอ → design-critic · แตะข้อมูล/ล็อกอิน/ไฟล์ → security-auditor) · ถ้าแตะฐานข้อมูล รัน `admin:live-contract` บน branch ก่อน merge และบน `main` หลัง merge
8. **ปิดงาน:** commit ระบุกฎที่แตะ เช่น `[R1,R16] …` · เปิด PR · รอ CI ผ่าน (`test` และ `e2e`) · merge เมื่อเงื่อนไขครบ · เขียนบันทึกสั้นใน `docs/learning/` และสรุปใน `docs/HANDOFF.md` พร้อม "รายการที่ต้องลองบนมือถือ"

ข้อควรจำ: เปลี่ยน UI ไม่ต้องแตะฐานข้อมูล · เปลี่ยนสูตรเงินต้องผ่านเทสต์และ money-auditor · อย่าเอาข้อมูลการเงินจริงใส่ในโค้ด เอกสาร หรือเทสต์

## 6. คำศัพท์ที่เจอบ่อย

| คำ | ความหมายสั้นๆ |
|---|---|
| สตางค์ / satang | หน่วยเงินจำนวนเต็ม 100 สตางค์ = 1 บาท |
| Entry / Line | รายการ / บรรทัดของรายการ (เดบิต บวก, เครดิต ลบ) |
| RLS | ฐานข้อมูลกรองแถวตามเจ้าของ |
| RPC | ฟังก์ชันในฐานข้อมูลที่เว็บเรียก |
| Migration | ไฟล์เปลี่ยนโครงสร้างฐานข้อมูลทีละขั้น |
| CSP | กฎของเบราว์เซอร์ว่าเว็บนี้โหลด/เรียกอะไรได้บ้าง |
| CI | ระบบรันเทสต์อัตโนมัติบน GitHub ทุก PR |
| live-contract | ชุดทดสอบที่รันกับ Supabase จริง (ใช้ผู้ใช้ทดสอบชั่วคราวที่ลบทิ้งหลังรัน) |
| harness | หน้าทดสอบสำหรับนักพัฒนา ใช้ข้อมูลสมมติในเบราว์เซอร์ ไม่ต่อฐานข้อมูลจริง |
