# ฐานข้อมูลตรวจบัญชีกับทุกการเขียน (PR แบบ draft · รออนุมัติ migration)

## ทำอะไร
- เว็บแนบ "รหัสผู้ใช้ที่หน้าจอนี้เป็นของ" ไปกับทุกคำขอ (หัวคำขอ `x-expected-user`)
- ฐานข้อมูลมีตัวตรวจ (trigger) บน 11 ตาราง: ถ้ารหัสนั้นไม่ตรงกับคนที่ล็อกอินอยู่ จะไม่เขียนอะไรเลย และเว็บบอกว่า "บัญชีที่เข้าสู่ระบบเปลี่ยนไป"
- หน้า US Stocks: ถ้าราคาบันทึกแล้วแต่อัตราแลกเปลี่ยนบันทึกไม่ได้ จะบอกตามจริง

## ทำไม
ทุกแท็บของเบราว์เซอร์ใช้การล็อกอินเดียวกัน ถ้าแท็บหนึ่งสลับบัญชี แท็บที่เปิดค้างอาจบันทึกข้อมูลลงบัญชีใหม่โดยไม่รู้ตัว
รอบก่อนกันไว้แล้วเฉพาะนำเข้า ล้าง และลบบัญชี รอบนี้ครอบการบันทึกรายการ บิล การลงทุน และค่าตั้งค่า

## ทำไมใช้ trigger
หลายคำสั่งเขียนตารางตรงๆ ไม่ผ่านฟังก์ชัน การทำ "ตัวห่อ" ทีละคำสั่งแบบรอบก่อนจะครอบไม่ครบ trigger อยู่ที่ตาราง จึงครอบทุกทางรวมถึงทางที่เพิ่มในอนาคต

## ข้อจำกัด
- กันความผิดพลาดของหน้าจอ ไม่ใช่ด่านกันคนอื่นเข้าถึงข้อมูล (งานนั้นเป็นของ RLS)
- แท็บรุ่นเก่าไม่ส่งรหัส จึงยังไม่ถูกตรวจจนกว่าจะรีเฟรช
- กันเฉพาะการเขียน แท็บค้างยังอ่านข้อมูลของบัญชีใหม่ได้ (คนเดียวกันที่ล็อกอินในเบราว์เซอร์นั้น)

## ทดสอบอย่างไร
- `npm test` เทสต์ใหม่ใช้ไลบรารี Supabase ตัวจริง ตรวจว่าหัวคำขอถูกส่งทุกชนิดคำสั่ง
- `supabase/tests/expected_user_header_test.sql` ลองเขียนผิดบัญชีทุกตาราง ต้องได้รหัส PT412
- ลองรันกับฐานข้อมูลจริงแบบย้อนกลับแล้ว ผ่าน 34/34 ไฟล์
- หลังใส่ migration (ต้องลองบนคอม บัญชีทดลองเท่านั้น): เปิดสองแท็บ แท็บสองสลับบัญชี กลับแท็บแรกแล้วเพิ่มบิล ต้องขึ้นว่าบัญชีเปลี่ยน
